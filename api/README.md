# Pokédex authentication API

A runnable email/password account API, separate from the existing Pokédex frontend. It uses Node.js 24, Express 5, Better Auth, and persistent SQLite. The frontend prototype still needs to be imported and connected to this API.

## Run locally

Use Node.js **24.15 or later within the 24.x line**, and npm. The built-in `node:sqlite` driver is supported by Better Auth; Node currently classifies that driver as a release candidate.

From the repository root:

```sh
cd api
npm ci
npm run setup
npm run db:migrate
npm run dev
```

The API listens on `127.0.0.1:3001` by default. Its configured public origin is `http://localhost:3001`. `GET /api/health` returns `{"status":"ok"}`. Use `npm start` without watch mode and `npm test` for the HTTP integration and configuration tests.

`setup` creates a local `.env` with a randomly generated secret, and preserves an existing `.env`. It does not print the secret. Migrations explicitly create/update the authentication tables and can be rerun. Startup refuses a missing/short secret or an unapplied schema; it does not silently migrate production data.

Accounts, sessions, and rate-limit counters live in `api/var/auth.sqlite` by default. Restarting the API preserves them. The generated configuration, database, SQLite sidecars, and dependencies are excluded from Git.

## Endpoints

Better Auth owns `/api/auth/*` and its request validation/error responses. Auth errors normally have top-level `code` and `message`; the custom `/api/me` and transport errors use an `error` object.

| Method | Path | Input / result |
| --- | --- | --- |
| POST | `/api/auth/sign-up/email` | `{name, email, password}`; creates an account and signed-in session |
| POST | `/api/auth/sign-in/email` | `{email, password, rememberMe?}`; sets the session cookie |
| POST | `/api/auth/sign-out` | `{}`; revokes the current session and clears its cookie |
| GET | `/api/auth/get-session` | Better Auth's current session/user response, or `null` |
| GET | `/api/me` | Safe user identity; `401` when unauthenticated |
| POST | `/api/auth/change-password` | `{currentPassword, newPassword, revokeOtherSessions: true}` |
| GET | `/api/auth/list-sessions` | Lists the authenticated user's active sessions |
| POST | `/api/auth/revoke-session` | `{token}`; revokes one of the authenticated user's sessions |
| POST | `/api/auth/revoke-sessions` | `{}`; revokes the authenticated user's sessions |
| GET | `/api/health` | Database connectivity check; no user/session data |

Names and email are required for registration. Password length is 15–128. Successful registration/sign-in currently returns `200`; duplicate registration returns `422`. Unknown email and incorrect password have the same sign-in error. Passwords are hashed through Better Auth's default scrypt implementation. No custom password cryptography is implemented here.

Sessions use signed, HTTP-only, host-only cookies with `SameSite=Lax`. Production adds `Secure`. The default lifetime is seven days, with renewal after one day of use. Cookie caching is disabled so session revocation takes effect on the next request. `/api/me` forwards renewed session cookies and only returns `id`, `name`, `email`, and `emailVerified`.

## Connect the frontend

For a separate development frontend, add its **exact origin**, for example `http://localhost:5173`, to `TRUSTED_ORIGINS` in `api/.env` and restart. Use the same hostname for frontend and API; `localhost` and `127.0.0.1` are different cookie sites.

```js
const apiOrigin = "http://localhost:3001";

async function request(path, body) {
  const response = await fetch(`${apiOrigin}${path}`, {
    method: body === undefined ? "GET" : "POST",
    credentials: "include",
    headers: body === undefined ? {} : { "Content-Type": "application/json" },
    body: body === undefined ? undefined : JSON.stringify(body),
  });
  const data = await response.json();
  if (!response.ok) {
    throw new Error(data.message ?? data.error?.message ?? "Request failed.");
  }
  return data;
}

// Values come from the user's form inputs.
await request("/api/auth/sign-in/email", { email, password });
const { user } = await request("/api/me");
await request("/api/auth/sign-out", {});
```

The browser manages the HTTP-only cookie. Use `user.id` as the account identity when trainer/tracker ownership is implemented; the demonstration trainer Seiko is not a login identity.

Keep deployed browser clients and the API on the same site, or proxy `/api` through the frontend origin. Credentialed CORS does not override `SameSite` cookie restrictions for unrelated sites.

## Configuration and operating limits

| Variable | Meaning |
| --- | --- |
| `BETTER_AUTH_SECRET` | Persistent signing/encryption secret, at least 32 characters; generated by `setup` |
| `BETTER_AUTH_URL` | Exact public API origin; explicitly required and HTTPS in production |
| `TRUSTED_ORIGINS` | Additional exact browser origins; no wildcards, paths, or credentials |
| `HOST`, `PORT` | Listen address/port; defaults `127.0.0.1`, `3001` |
| `DATABASE_PATH` | SQLite filename, resolved relative to `api/` |
| `TRUST_PROXY_CIDRS` | Explicit IPs/CIDRs of operated reverse proxies; empty means forwarded IPs are ignored |
| `SESSION_TTL_SECONDS` | Session lifetime; default 604800, allowed 3600–2592000 |

State-changing browser requests retain Better Auth's origin/CSRF checks. Credentialed CORS is limited to the configured origins. Bodies, including chunked requests, are capped at 16 KiB before reaching authentication. Responses use `Cache-Control: no-store` and Helmet headers. Logs omit request bodies, cookies, tokens, and library error details.

Rate limiting is enabled in development and production and persisted in SQLite: sign-in 10/minute/IP, registration 3/minute/IP, password change 3/minute/IP, and 100/minute/IP for other authentication paths. A `429` includes **`X-Retry-After`** in seconds, exposed to allowed browser origins. The server overwrites the internal IP header from Express's socket-aware proxy policy. A public reverse proxy needs explicit trusted proxy addresses and a private origin; configure that deployment's actual network rather than trusting arbitrary forwarded headers.

This first backend targets one Node process with a persistent local SQLite volume. A distributed/serverless deployment needs a shared database and a deliberate shared rate-limit/session configuration. Store and back up the database and secret together as private operational data. Run migrations explicitly when upgrading the pinned authentication dependencies.

Email verification and forgotten-password email delivery are **not configured**. New accounts have `emailVerified: false`; an email address is not proof of mailbox ownership. Add an email sender and the verification/recovery flow before relying on verified email identity. Social login, MFA, trainer/tracker cloud saves, frontend forms, and deployment are separate work.

## Verification

`npm test` uses real local HTTP requests and isolated temporary SQLite files. It covers registration/hashing, sign-in failures, uniqueness, cookies, protected identity, restarts, session expiry/tampering/revocation, password change, origin/CSRF rejection, credentialed CORS, persistent throttling/IP spoofing, body limits, and startup configuration. Tests create no external accounts and send no email.

Dependency audit: `npm audit --omit=dev`. The lockfile pins the installed tree. The workflow in [auth-api.yml](../.github/workflows/auth-api.yml) installs from that lockfile and runs the tests on Node 24.
